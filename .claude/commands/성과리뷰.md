$ARGUMENTS 인자로 **성과 리뷰 (C-9 단독)** 를 실행해줘.

## 명령 정보

- **모듈:** C-9 단독 분리 실행 (briefing_module_CDE.md)
- **산출물:** `reports/briefing/performance_review_{기간}_{YYYYMMDD}.html`
- **차이 vs /주간리포트:** 주간리포트는 C-1~C-10 + C-9 부속, 성과리뷰는 C-9 단독 + 더 긴 기간

## 인자 해석

- 인자 없음 → `1m` (최근 1개월 ≒ 22영업일)
- `1w` → 최근 1주
- `2w` → 최근 2주
- `1m` → 최근 1개월
- `3m` → 최근 3개월
- `--html` → HTML 생성 (기본)

## ★ 후속 단계 — 애널리스트 사후 평가 (analyst-scraper outcome_eval 모드)

**위임 책임**: briefing-lead 가 본인 제안 적중률 평가 (C-9) 완료 직후, **briefing-lead 가 직접 Task(subagent_type="analyst-scraper")** 로 outcome_eval 모드 호출 (메인 추가 dispatch 불요). briefing-lead 가 도구 부재 (Task 미부여 슬롯) 시에만 메인이 fallback dispatch.

호출 컨텍스트:

```
mode: outcome_eval
period: {본 명령의 period 인자 그대로}
reference_date: {오늘 KST}
target: reports/analyst/items/*/ 중 outcome=null 이고 평가 시점 도달한 항목 (per call ≤ 20건)
```

analyst-scraper 가:

1. 평가 시점 도달 항목 식별 (발행일 + 목표 기간의 50% 경과)
2. 가격 조회 (knowledge-db/market 또는 WebSearch)
3. meta.outcome 채움 (hit / error_pct / thesis_validity / notes)
4. summary.html 재생성 (process_analyst_web.py commit)
5. 결과 보고 (평가 N건, 분석가별 점수 변화)

메인이 결과를 받아 `performance_review_{period}_{YYYYMMDD}.html` 의 마지막에 **"애널리스트 사후 평가" 섹션** 추가:

- 본 기간 신규 평가 N건 (적중 / 미적중 / 진행 중)
- 분석가별 누적 점수 표 (Top 3 + Bottom 1)
- /analyst/scoreboard 링크

평가 가능 항목 0건 (모두 평가 시점 미도달) 이면 섹션 생략 + "다음 평가 가능 시점: YYYY-MM-DD (X 항목)" 안내.

### 평가 가능 시점 가이드

| 목표 기간                           | 평가 가능 시점        |
| ----------------------------------- | --------------------- |
| 단기 콜 (period=N/A or EOY 1~3개월) | 발행 후 30일+         |
| 6M target                           | 발행 + 3개월          |
| 12M target                          | 발행 + 6개월          |
| EOY target                          | 발행~연말 의 50% 경과 |

### 중복 평가 방지

- meta.outcome.evaluated_at 이 7일 이내면 skip (재평가 안 함)
- 7일 이상 지난 outcome 은 갱신 가능 (시장 변동 반영)

## ★ 후속 단계 — 데일리픽 논지 판정

같은 종목이 다시 DailyPick 으로 추천됐을 때, 재추천의 논지가 anchor(묶음 기준) 분석과 같은지(동일/보강) 바뀌었는지(전환) 를 판정해 성적표의 묶음/분리를 결정한다. 매주 /성과리뷰 에서 미판정 재픽을 처리한다.

절차 (작업 디렉토리 = 프로젝트 루트):

1. 무효 판정 정리: `cd web && node scripts/build_daily_pick_eval.mjs --prune-invalid`
2. 대상 확인: `node scripts/build_daily_pick_eval.mjs --queue` (읽기 전용 JSON). 0건이면 이 절 전체 생략.
3. 티커별로 아래 루프를 수행한다. 두 가지 방식 중 하나:
   - **메인 인라인(순차)**: 메인이 직접 판정하며 5단계에서 `web/src/data/daily_pick_thesis.json` 에 바로 append 해도 된다.
   - **티커당 general-purpose 에이전트(병렬)**: 이 절의 기준표·형식·금지를 프롬프트에 그대로 전달. 에이전트는 공유 파일 `daily_pick_thesis.json` 을 **절대 쓰지 않는다** (동시 쓰기 충돌·JSON 깨짐 방지). 대신 세션 scratch 디렉토리의 자기 전용 파일 `<scratch>/thesis_<T>.json`(절대경로, 처음엔 `[]`)에 판정 행을 append 하고, 루프 1단계를 `node scripts/build_daily_pick_eval.mjs --queue --ticker <T> --judgments-extra <scratch>/thesis_<T>.json` 으로 돌려 자기 판정을 반영한 다음 재픽을 받는다. 병합은 3.5 단계에서 메인이 한다.
   1. `node scripts/build_daily_pick_eval.mjs --queue --ticker <T>` (병렬 에이전트는 위의 `--judgments-extra <자기 파일>` 추가) → 항목이 없으면 그 티커 종료.
   2. 가장 이른 미판정 재픽 1건의 anchor_analysis_dir / analysis_dir 와 anchor_source / target_source 확인. **anchor_source 또는 target_source 가 `missing` 이면 그 티커를 건너뛰고 보고한다 — 원문 없이 추측 판정 금지.**
   3. 두 분석의 원문을 읽는다 (필요한 부분만 head/grep, 큰 파일 통째 금지):
      - `live:analysis/<dir>/<file>` → 해당 폴더에서 직접 Read.
      - `archive:analysis/_archive/<tar>` → `tar -xzOf "analysis/_archive/<tar>" "<dir>/scorecard.md"` 로 stdout 읽기 (디스크에 풀지 말 것). 있으면 `<dir>/_report_data.json`(thesis·executive_summary), `<dir>/business.md` 앞부분도. 내부 한글 경로가 NFD 면 `tar -tzf` 로 실제 이름 확인.
   4. 기준표 3항목: ① 핵심 성장 동력 ② 밸류에이션 근거(왜 지금 사도 되는가) ③ 핵심 촉매·리스크.
      - 셋 다 같음 → `동일`
      - ①이 같고 ②③에 근거 추가·갱신 → `보강`
      - ①이 바뀜(다른 사업·다른 수요 동인이 주 논거) → `전환`
      - 점수·목표가·등급 숫자 변화만으로는 전환이 아니다. 주 논거(무엇이 이 회사를 사게 만드는가)가 바뀌었는지만 본다. ETF 는 ① = 노출 대상·편입 논리 (예: 배당성장, 단기국채 현금대용).
   5. 판정 행 1개를 **append only** — 메인 인라인은 `web/src/data/daily_pick_thesis.json`, 병렬 에이전트는 자기 `<scratch>/thesis_<T>.json` (JSON 유효성 유지, 기존 행 수정·삭제 금지):
      `{"date": <item.date>, "ticker": <T>, "anchor_date": <item.anchor_date>, "anchor_version": <item.anchor_version>, "version": <item.version>, "verdict": "동일"|"보강"|"전환", "rationale": "<120자 이내: v{a} 근거=… / v{b}=… → 판정>", "judged_at": "<오늘 KST>", "judged_by": "agent"}`
      date / anchor_date / anchor_version / version 은 큐 항목 값을 그대로 복사.
   6. 1로 돌아간다 (다음 재픽이 나온다. 전환이면 anchor 가 바뀐 항목이 나온다). 한 티커 루프가 30회를 넘으면 멈추고 보고.
3.5 (병렬 에이전트를 쓴 경우만) 모든 에이전트 종료 후 메인이 병합한다. 각 `thesis_<T>.json` 에 대해 검증: ① JSON 파싱 성공·배열 ② 각 행 필수 필드(date·ticker·anchor_date·anchor_version·version·verdict·rationale·judged_at·judged_by) 존재 ③ verdict ∈ {동일, 보강, 전환} ④ `ticker@date` 가 파일 안에서도, 기존 `daily_pick_thesis.json` 행과도 중복되지 않음 ⑤ ticker 가 파일명의 <T> 와 일치. 통과한 행만 `daily_pick_thesis.json` 끝에 append (기존 행 수정 금지), 실패 행·파일은 버리고 보고.
4. `node scripts/build_daily_pick_eval.mjs` 재실행 → `--queue` 로 pending 0건 확인 (`missing` 으로 건너뛴 티커는 남아 있어도 된다 — 보고에 명시).
5. `--prune-invalid` 가 0건 제거했고 큐도 0건이라 thesis 파일이 바뀌지 않았다면 커밋하지 않는다 (eval 의 generated_at 만 바뀐 커밋 금지). thesis 파일이 변경된 경우에만 커밋 (아래 두 파일만): `git add web/src/data/daily_pick_thesis.json web/src/data/daily_pick_eval.json` → 메시지 `data(daily_pick): 주간 논지 판정 N건`.

**판정은 동결**: 한 번 기록된 행은 수정하지 않는다. 판정을 바꾸려면 사람이 override 파일만 편집한다. 위임 에이전트는 서브에이전트를 생성하지 않으며 `.env*` 를 읽지 않는다.
