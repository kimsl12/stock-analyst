# 재분석 자동 실행 (Re-analysis Auto-run)

`$1` 일 이상 경과 분석 중 우선순위 상위 `$2` 종목을 **앵커링 편향 없이** 재분석한다.
인자 생략 시 기본값: `$1=14`, `$2=5`. **사용자 승인 게이트 없음 — 인자 자체가 cap.**

## 인자 파싱 + 안전장치

```bash
THRESHOLD_DAYS=${1:-14}
TOP_N=${2:-5}
# 상한 캡 — 1회 실행 = 토큰/시간 폭주 차단
[ "$TOP_N" -gt 10 ] && TOP_N=10
[ "$THRESHOLD_DAYS" -lt 7 ] && THRESHOLD_DAYS=7   # 7일 미만은 의미 없음
echo "임계 ${THRESHOLD_DAYS}일 / 상한 ${TOP_N}종"
```

자동 안전장치:
- `TOP_N > 10` → 10으로 클램핑 (사용자 입력 오타 방어)
- 후보 0종 → 즉시 종료 (Phase 1 진입 안 함)
- 개별 종목 실패 → 2회 재시도 후 SKIP (다른 종목으로 진행, 전체 중단 ❌)
- 중간 실패 → 그 시점까지의 성공분만 묶음 commit (rollback 안 함)

## Phase 0: 검출 (재분석점검 로직 재사용)

`/재분석점검 ${THRESHOLD_DAYS}` 와 동일한 알고리즘으로 stale 후보를 추출한다.
**단, 본 명령은 보고하지 않고 곧바로 Phase 1로 진입한다.**

```bash
today=$(date +%Y-%m-%d)
today_sec=$(date -j -f "%Y-%m-%d" "$today" "+%s" 2>/dev/null || date -d "$today" "+%s")

# session-bootstrap.md 의 "| {종목} | {날짜} | {스코어}" 행 추출
# → days|stock|date|score 4필드 정렬 (경과일 desc)
candidates=$(grep -E "^\| [A-Z0-9_가-힣]+" session-bootstrap.md | \
    awk -F'|' '{ print $2 "|" $3 "|" $4 }' | while IFS='|' read -r stock date rest; do
        stock=$(echo "$stock" | xargs)
        date=$(echo "$date" | xargs | cut -c1-10)
        [[ -z "$date" || ! "$date" =~ ^2026 ]] && continue
        date_sec=$(date -j -f "%Y-%m-%d" "$date" "+%s" 2>/dev/null || date -d "$date" "+%s")
        days=$(( (today_sec - date_sec) / 86400 ))
        # 임계 ≥ THRESHOLD 또는 (≥7일 + 섹터 KB 7일 내 갱신) → HIGH
        [ $days -ge "$THRESHOLD_DAYS" ] && echo "$days|$stock|$date|$(echo $rest | xargs)"
    done | sort -rn -t'|' -k1 | head -n "$TOP_N")

# 후보 0종 — 즉시 종료
[ -z "$candidates" ] && {
    echo "🟢 임계 ${THRESHOLD_DAYS}일+ 경과 종목 없음 — 재분석 불요"
    exit 0
}

# 표 출력 (사용자가 작업 시작 직전 무엇이 처리되는지 확인)
echo "## 재분석 대상 (${TOP_N} 상한 적용)"
echo "$candidates" | awk -F'|' '{ printf "%d. %s (%s, %d일, 이전 %s)\n", NR, $2, $3, $1, $4 }'
```

> ⚠️ 본 명령은 사용자 게이트가 없으므로, Phase 0 표 출력 직후 5초 안에 Phase 1로 진입한다.
> 사용자가 중단하려면 Ctrl+C — 그 외 자동 진행.

## Phase 1: BLIND 재분석 (앵커링 차단)

각 후보 종목 `{티커}` 에 대해 `/종목분석 {티커}` 와 동등한 워크플로우(Phase 0~3)를 실행한다.
**단, 5명 분석가 + scorecard-strategist 가 이전 분석 파일을 절대 read 하지 않도록 구조적으로 차단한다.**

### 핵심 규칙: --reanalysis 모드 자동 부여

리드는 각 종목 분석 호출 시 **컨텍스트 플래그 `--reanalysis`** 를 자동 부여한다.
이 플래그는 다음 의미를 갖는다:

```
--reanalysis 플래그 시 적용되는 행동 변경:

1. data-collector
   - 이전 분석 산출물 (analysis/{티커}_*v*/, reports/{티커}_*.html) 절대 읽지 않음
   - 신규 데이터만 수집 (현재가, 최근 실적, 컨센서스, 뉴스) → analysis/{티커}_v{N}/data.json
   - 이전 v{N-1} 폴더는 존재 무시

2. company-overview / financial-analyst / business-analyst / momentum-analyst / risk-analyst
   - analysis/{티커}_v{N}/ 안의 동일 세션 산출물 + KB 만 read
   - analysis/{티커}_v{N-1}/, reports/{티커}_*.html 절대 read 금지 (Glob/Read 시도 시 자체 차단)
   - "이전 분석에서는 X였으나" 같은 비교 문장 금지 — 이전 모름

3. scorecard-strategist
   - 동일 세션 analysis/{티커}_v{N}/*.md 만 종합
   - 이전 스코어/등급 모름 → 새로 점수 산출
   - **본문 의무**: confidence interval (목표가 ±X%, 스코어 ±N점) + 약한 가정 3개 명시
     ("이 결론을 뒤집을 수 있는 핵심 가정 3개" 본문 §X 별도 섹션)

4. report-generator
   - HTML 출력 시 "재분석 v{N} (이전 v{N-1} 비교 미포함)" 헤더만 추가
   - 비교표는 Phase 2 의 reanalysis-tracker 가 별도 섹션으로 추가
```

> ⚠️ **앵커링 편향 차단의 핵심은 구조적 분리.**
> 휴리스틱 프롬프트("이전과 다르면 의심하라")는 틀린 분석을 학습할 위험이 있다.
> 분석가가 이전 결과를 모르면, 같은 회사의 같은 데이터에서 다른 결론이 나와도
> 그 결론은 "현재 데이터로부터의 독립 추론"이지 "이전 결론으로부터의 보정"이 아니다.

### 종목당 실행 절차 (리드가 직접 루프)

```
for 각 후보 티커 in candidates:
    # v{N} 결정 (기존 v1, v2, ... 중 가장 큰 + 1)
    EXISTING=$(ls -d analysis/{티커}_*_v*/ 2>/dev/null | sed 's/.*_v\([0-9]*\)\/$/\1/' | sort -n | tail -1)
    NEXT_V=$(( ${EXISTING:-1} + 1 ))   # v1 → v2, v2 → v3 ...
    [ -z "$EXISTING" ] && {
        # v 접미사 없는 폴더 → v1 으로 리네임 후 v2 시작
        mv analysis/{티커}_{종목명}/ analysis/{티커}_{종목명}_v1/
        NEXT_V=2
    }

    # 해당 종목에 대해 Phase 0-A ~ Phase 4 실행
    # — 모든 호출에 "--reanalysis 모드, 출력 폴더 analysis/{티커}_{종목명}_v{NEXT_V}/" 명시
    # — 분석가 프롬프트에 "이전 v{N-1} 절대 read 금지" 의무 문장 포함
    # — [v3.20, 2026-05-13] 모든 lead dispatch 프롬프트에 다음 fallback 명시 필수:
    #
    #   "서브에이전트 dispatch 도구(Agent/Task/Write/Edit)가 부재한 슬롯 가능성 있음.
    #    감지 시 즉시 stock-analyst-lead.md '리드 직접 수행 모드 (Fallback)' 절을 적용해
    #    리드 자신이 KB read + fetch_price.py + 공개 지식 기반으로 BLIND v{N} 7개 파일
    #    (data.json, company.md, financial.md, business.md, momentum.md, risk.md, scorecard.md)
    #    을 직접 작성하라. '도구 부재'를 사유로 한 조기 중단 및 SKIP 금지 — 회차 보고에서
    #    스킵 사유로 '도구 부재' 가 등장하면 본 명령은 실패한 것으로 간주된다."

    # 종목당 실행 결과:
    #   analysis/{티커}_{종목명}_v{N}/   (data.json + 6개 .md)
    #   reports/{티커}_{종목명}_{YYYYMMDD}.html
    # 단, 종목당 commit 은 Phase 3 묶음 commit 으로 미룬다.
```

### 종목당 실패 처리 (개별 SKIP, 전체 중단 ❌)

```
[규칙 0 — v3.20] "도구 부재" 사유 SKIP 금지
  - lead 가 Agent/Task/Write 도구 부재를 사유로 SKIP 보고하면 본 명령은 실패.
  - 반드시 stock-analyst-lead.md "리드 직접 수행 모드 (Fallback)" 적용해 직접 작성 후 진행.
  - 적용 증거: 2026-05-13 (2회차) COST 가 같은 Read+Bash 제약에서 fallback 으로 v3 완성.
    → 같은 제약 = 같은 결과 가능. 다른 결과는 lead 자기 판단 분기 차이일 뿐.
  - SKIP 보고에서 사유가 "Agent/Write 부재" / "도구 미부여" / "schema 없음" 으로 시작하면
    리드는 즉시 fallback 모드로 재진입해야 한다 (재시도 횟수 카운트 X).

[규칙 1] 같은 티커 2회 재시도 후 실패 (도구 부재 외 사유) → SKIP
  - 실패 사유 기록 (data 수집 실패 / Phase 1 분석가 응답 없음 / scorecard 실패 등)
  - 다음 후보 진행
  - Phase 4 보고에 "❌ {티커}: SKIP ({사유})" 명시

[규칙 2] 토큰 한도 도달 → 그 시점까지 완료된 종목만 Phase 3 commit 후 종료
  - 미진행분은 Phase 4 보고에 "⏸ {티커}: 토큰 한도로 미실행" 명시

[규칙 3] 후보 절반(=N/2) 이상 SKIP → 전체 중단
  - 환경 문제(API 한도, 네트워크) 의심 — Phase 3 commit 진행 후 사용자 보고
  - 단 SKIP 사유가 모두 "도구 부재" 라면 환경 문제가 아닌 lead 자기 판단 오류 → 규칙 0 적용
```

## Phase 2: 변화 추적 (reanalysis-tracker)

Phase 1의 모든 종목 분석이 끝난 뒤, 리드가 **별도 비교 단계**를 수행한다.
이 단계는 분석 자체에 영향을 주지 않으며, **순수 read-only 비교 보고**다.

### 비교 입력 (read-only)

각 재분석 완료 종목 `{티커}` 에 대해:

```
입력 1: analysis/{티커}_{종목명}_v{N}/scorecard.md   (Phase 1 신규)
입력 2: analysis/{티커}_{종목명}_v{N-1}/scorecard.md (이전, 비교용)
입력 3: reports/{티커}_*_{이전날짜}.html              (이전 HTML, 등급/목표가 추출)
```

### 비교 항목 추출 (Bash + Grep)

```bash
# 종목당 변화 추적 데이터 수집
for ticker in completed_tickers:
    NEW_DIR="analysis/{티커}_{종목명}_v${NEXT_V}"
    OLD_DIR="analysis/{티커}_{종목명}_v$((NEXT_V-1))"

    # 스코어 (예: "**종합 점수: 72/100**")
    NEW_SCORE=$(grep -oE '종합[^0-9]*[0-9]+' $NEW_DIR/scorecard.md | head -1)
    OLD_SCORE=$(grep -oE '종합[^0-9]*[0-9]+' $OLD_DIR/scorecard.md | head -1)

    # 등급 (예: "투자등급: 매수")
    NEW_GRADE=$(grep -oE '(강력매수|매수|중립|매도|강력매도)' $NEW_DIR/scorecard.md | head -1)
    OLD_GRADE=$(grep -oE '(강력매수|매수|중립|매도|강력매도)' $OLD_DIR/scorecard.md | head -1)

    # 목표가
    NEW_TP=$(grep -oE '목표[^0-9]*[\$₩,0-9.]+' $NEW_DIR/scorecard.md | head -1)
    OLD_TP=$(grep -oE '목표[^0-9]*[\$₩,0-9.]+' $OLD_DIR/scorecard.md | head -1)
done
```

- 🔴 → 🟢: 없음

### scorecard.md 본문 의무 (앵커링 보강)

각 신규 스코어카드 본문에 다음 두 섹션을 의무 포함한다 (scorecard-strategist 책임):

1. **§ Confidence Interval**
   - 목표가 ±X% (95% CI 또는 시나리오 분기 폭)
   - 스코어 ±N pt (가정 변경 시 변동 폭)
2. **§ 약한 가정 3개 (Most Fragile Assumptions)**
   - 결론을 뒤집을 수 있는 가정 3개
   - 각 가정별 "반증 시 영향" 1줄

## Phase 3: 묶음 commit + push + deploy

Phase 1+2+2.5 완료 후, 리드가 **단일 commit 으로 묶음** 처리한다.

```bash
# 본 회차 신규 산출물만 add (다른 진행 중 작업 섞임 방지)
for ticker in completed_tickers:
    git add analysis/{티커}_{종목명}_v${N}/        # active v{N}
    git add analysis/{티커}_{종목명}_v$((N-1))/    # active v{N-1} (옛것 archive 이동)
    git add reports/{티커}_{종목명}_${YYYYMMDD}.html
    git add session-bootstrap.md   # 마지막 분석 갱신
done
git add analysis/_reanalysis_runs/${YYYYMMDD}_run.md
git add analysis/_history/                        # timeline.json 갱신
# analysis/_archive/, reports/_archive/ 는 .gitignore (git 무시 — 로컬 유지)

# 묶음 commit (HTML + analysis/ + history)
SUMMARY=$(echo "$completed" | wc -l)
SKIPPED=$(echo "$skipped" | wc -l)
git commit -m "$(cat <<EOF
analysis(reanalysis): ${TODAY} 재분석 ${SUMMARY}종 (스킵 ${SKIPPED}종)

대상: ${completed_tickers_csv}
임계: ${THRESHOLD_DAYS}일 / 상한 ${TOP_N}종

Co-Authored-By: Claude
EOF
)"

# manifest 동기화 [v3.16 — 2026-05-10] — HTML commit 후 호출 (정확한 sort_key 추출)
#   Vercel 빌드 컨테이너에 .git 미포함 → manifest.json sort_key 가 commit snapshot 이어야 함.
#   commit 후 호출해야 build_manifest 의 git log 가 정확한 commit time 잡음.
if (cd web && node scripts/build_manifest.mjs); then
  if ! git diff --quiet web/src/data/manifest.json; then
    git add web/src/data/manifest.json
    git commit -m "chore(manifest): ${TODAY} 재분석 ${SUMMARY}종 동기화"
  fi
else
  echo "⚠️ build_manifest 실패 — manifest 미동기화 (push 진행, 본서버는 직전 snapshot 사용)"
fi

git pull --rebase origin main
git push origin main
```

## 매주 루틴화 (선택)

이 명령을 cron 또는 사용자 수동 호출로 매주 실행 가능.

```
권장 주기: 매주 월요일 (주말 동안 누적된 데이터 + 새 KB 갱신 반영)
권장 인자: /재분석실행 14 5
  → 14일+ 경과 상위 5종 자동 재분석
  → 1회 실행 약 25~40분 (5종 병렬 시)
```

## 주의사항

- 본 명령은 **자동 실행** 명령이다. Phase 0 검출 직후 사용자 확인 없이 Phase 1로 진입한다.
  - 사용자 게이트가 필요하면 `/재분석점검 ${THRESHOLD_DAYS}` 사용 (보고만, 실행 없음)
- BLIND 모드는 분석가의 자유도를 의도적으로 제한한다.
  - 같은 회사를 재분석할 때 등급이 자주 바뀌는 것이 정상 (시그널이 누적되는 만큼 결론도 갱신).
  - 등급이 자주 안 바뀌면 → KB 갱신이 부족하거나 데이터가 stale.
- 재분석 1회 비용 = 종목당 약 5~8분 + 토큰 (5종 병렬 시 25~40분).
  - `TOP_N=10` 으로 늘리면 50~80분 소요 가능. 시간/토큰 예산 고려.

## 실패 케이스

- 후보 0종 → "🟢 임계 ${THRESHOLD_DAYS}일+ 경과 종목 없음 — 재분석 불요" (정상 종료)
